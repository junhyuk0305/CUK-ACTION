# CUK Action 운영 반영 점검 (2026-11-26)

통합본을 운영 DB에 반영했다. 핵심 흐름 10개를 브라우저로 두 번 통과시켰다. 처음 시도(77bea86)는 CLI가 다른 Supabase 계정에 로그인돼 있어 403으로 멈췄다. 사용자가 다시 로그인한 뒤 1단계부터 진행했다.

Netlify 배포, push, main 병합은 하지 않았다. Gemini는 호출하지 않았고 학교 홈페이지에도 요청을 보내지 않았다. 브라우저 점검은 catholic.ac.kr 요청을 모두 막은 상태로 했고, 막힌 요청은 0건이었다.

## 5. 고치지 못한 것

- 운영 DB에 문항을 지우는 요청을 직접 보내 거절되는지 보는 시험은 하지 않았다. 거절되지 않으면 시연 공고가 실제로 바뀌기 때문이다. 화면은 구조 칸을 잠그고, DB 잠금 거절은 로컬 DB 테스트가 확인한다.
- 전체 대시보드에 사이트 공고와 외부 공고가 섞이면 첫 네 칸이 사이트 단계를 먼저 보인다. 외부 공고만 가진 담당자는 예전과 같다.
- 신청서의 자격 판정은 제출 시점 값이다. 담당자가 신고를 확인해도 그 신청서의 판정은 다시 계산하지 않는다. 약속 문서의 알려진 한계다.

## 7. Gemini 키를 넣은 뒤 확인할 것

- 링크 초안: 실제 학교 공지 주소로 초안을 만들고 칸별 원문 근거가 맞는지 본다. 같은 원문의 학교 공고가 있으면 중복 안내와 게시 종료 확인이 뜨는지 본다. 학교 페이지 본문 영역 이름은 아직 실제 페이지로 확인하지 않았다.
- 이미지로만 된 공고와 명단이 있는 공고에서 AI를 부르지 않고 안내만 보이는지 본다.
- AI 수정 제안: 장학 공고에서 제안 블록이 실제 이탈 구간(두 번째 블록)과 맞는지 본다. 적용을 누르면 편집기 글이 바뀌고 학생 화면에 반영되는지 본다.
- 서버 함수 환경 변수 `GEMINI_API_KEY`와 선택 `GEMINI_MODEL`을 넣은 뒤 함수를 다시 배포할 필요는 없다. 비밀 값만 넣으면 된다.
