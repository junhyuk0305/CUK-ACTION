# 밤샘 지시문: 학생 쪽

너는 CUK Action의 학생 쪽 기능을 밤새 혼자 구현한다. 사용자는 자고 있다. 질문하지 말고 끝까지 진행한다.

## 먼저 읽을 것

1. `docs/CONTRACT.md`. 데이터 약속이다. 이름과 모양을 그대로 따른다.
2. `../자료/CUK Action 본선 최종안.md`. 무엇을 만드는지와 그 이유.
3. `../자료/CUK Action 구현 계획.md`의 "파일 소유", "두 쪽이 만나는 지점".
4. `../AGENTS.md`와 `../자료/본선 공고 데이터 사용 기준.md`. 학교 공고를 다루는 규칙.
5. `docs/tasks/FOUNDATION.md`의 "마지막 보고". 기반이 실제로 어떻게 만들어졌는지와 테스트 준비 함수 쓰는 법.

## 상황

- 대회 제출용 프로젝트다. 실제 사용자는 없다. 실서비스처럼 보이고 동작하는 것이 목표다.
- 담당자 쪽은 다른 세션이 다른 작업 폴더에서 동시에 만든다. 아침에 합친다.
- 공통 기반은 이미 커밋돼 있다. 테이블, 읽기 권한, `src/contract.js`, 빈 틀 파일이 있다.
- `src/main.jsx`는 한 줄이 매우 길다. 새 화면은 새 파일로 만들고 `main.jsx`에는 연결만 넣는다.

## 규칙

- 질문하지 않는다. 막히면 가장 단순한 기본값으로 진행하고 아래 "진행 기록"에 적는다.
- 내 파일만 고친다.
  - 고쳐도 되는 파일: `src/main.jsx`, `src/campus.jsx`, `src/IdAuth.jsx`, `src/Account.jsx`, `src/useStudentState.js`, `src/data.js`, `src/ApplicationForm.jsx`, `src/NoticeBlocks.jsx`, `src/student-api.js`, `src/student.css`, `src/campus.css`, 새로 만드는 학생 파일.
  - 마이그레이션은 `supabase/migrations/2026112601xx_이름.sql`로 새로 만든다.
  - 테스트는 새 파일로 만든다. DB 테스트는 `scripts/test-db-student.mjs`에 쓴다.
- 고치지 않는 파일: `src/contract.js`, `docs/CONTRACT.md`, 기반 마이그레이션, `src/backend.js`, `src/gateway.js`, `src/logic.js`, `package.json`, `src/Manager.jsx`, `src/ManagerOverview.jsx`, `src/WorkflowFields.jsx`, `src/manager-api.js`, `supabase/functions/` 아래.
- 고치지 않는 파일을 바꿔야 하면 바꾸지 않고 "통합 요청"에 적는다.
- 담당자 쪽 함수가 필요한 테스트는 테이블에 직접 넣어서 한다. 예: 공고 줄, 확인된 자격 줄.
- `ApplicationForm`과 `NoticeBlocks`의 props는 `CONTRACT.md` 7절 그대로 둔다. 담당자 쪽이 미리보기에서 가져다 쓴다.
- 운영 DB에 접속하지 않는다. 배포하지 않는다. push하지 않는다.
- 브라우저를 띄우지 않는다. 묶음이 끝나면 `npm run build`, `npm test`, `npm run test:db`만 돌린다.
- 실패한 테스트를 지우거나 건너뛰지 않는다. 못 고치면 기록하고 다음 묶음으로 간다.
- 묶음이 끝날 때마다 커밋한다. 커밋 메시지는 영어 한 줄로 쓴다.
- 묶음 구현은 가능하면 하위 에이전트에 맡긴다. 본 세션은 약속과 진행 기록을 쥔다.
- 기존 디자인 시스템을 따른다. 새 색, 새 글꼴, 새 부품 모양을 만들지 않는다. `student.css`의 기존 클래스를 먼저 쓴다.
- 화면 문구 규칙: 한 문장에 한 가지. 능동태. 꾸미는 말 없음. 대시와 중간점으로 잇지 않음. 라벨과 상태는 명사형.
- 새 기능은 실제 DB 통로만 만든다. `gateway.js`의 테스트용 통로에는 넣지 않는다.
- 학생 프로필, 지원서 답변, 자기 신고 설명은 AI에 보내지 않는다.

## 묶음

위에서부터 순서대로 한다. 순서가 시연 중요도다.

### S1. 목록과 상세

- 공고 카드와 상세에 신청 방식 표시를 붙인다. "사이트 신청", "외부 신청". `applyMode`로 정한다.
- 학교 공고에는 출처 줄을 붙인다. 부서, 게시일, 원문 링크. 학교 공고는 `sourceArchiveId`가 있는 공고다.
- 로그인 후 상세에도 "AI가 정리한 정보이니 원문을 확인하세요"를 넣는다. AI 안내가 있는 공고에만 보여 준다.
- `NoticeBlocks`를 구현한다. `noticeBlocks(notice)`로 읽고 종류별로 그린다. 블록마다 `data-block-id`를 붙인다. `onReach`는 블록이 절반 이상 1초 보이면 한 번 부른다.
- 로그인 후 상세와 공개 상세의 본문을 `NoticeBlocks`로 바꾼다.
- 사이트 접수 공고의 상세에는 "신청하기" 버튼을 둔다. 외부 신청 공고는 지금 흐름 그대로다. "공식 접수 미연동" 문구는 외부 신청 공고에만 남긴다.
- 끝 기준: 단위 테스트로 발췌만 있는 공고가 `x1`, `x2` 블록으로 나오는지 확인한다.

### S2. 신청서

- `ApplicationForm`을 구현한다. 문항 종류별 입력 칸을 그린다.
- 신청서 화면을 새 파일로 만든다. 순서는 기본 정보, 자격 확인, 문항, 제출이다.
- 기본 정보 문항은 프로필 값으로 미리 채운다. 학생이 고칠 수 있다.
- 자격 확인에는 공고 자격마다 학생 값과 판정을 보여 준다. 판정은 `eligibility()`를 쓴다. 값이 없는 자격은 그 자리에서 입력한다.
- 미충족 자격이 있으면 제출 위에 "충족하지 않는 조건이 있습니다. 신청은 할 수 있고 담당자가 확인합니다"를 보여 준다. 제출은 막지 않는다.
- 작성 중인 답은 `student_state`의 `applications[공고 id].draft`에 자동 저장한다.
- 제출을 누르면 확인 창을 띄운다. 신청서에서 새로 넣거나 고친 프로필 값을 나열하고 "내 정보에도 저장"을 묻는다. 학생이 확인한 값만 프로필에 저장한다.
- `submit_application`, `withdraw_application` 함수를 만든다. 규칙은 `CONTRACT.md` 6절.
- 제출 뒤에는 마감 전까지 수정과 취소를 할 수 있다. "내 신청"에 제출 상태를 보여 준다.
- 끝 기준: 로컬 DB 테스트에서 제출하면 신청서 한 줄이 생긴다. 다시 제출하면 같은 줄이 바뀐다. 마감 지난 공고, 외부 신청 공고, 필수 문항이 빈 제출은 거절된다. 다른 학생의 신청서를 읽지 못한다.

### S3. 측정 수집

- `record_event` 함수를 만든다. 규칙은 `CONTRACT.md` 5절과 6절.
- 상세를 열 때 `view`를 유입과 함께 기록한다. 기존 `view` 기록을 이 함수로 바꾼다. 한 번만 기록한다.
- 유입은 주소의 `?src=` 값으로 정한다. 값이 없으면 목록에서 들어온 경우 `browse`, 주소로 바로 들어온 경우 `direct`다.
- `NoticeBlocks`의 `onReach`에서 `block`을 기록한다.
- 신청서를 열 때 `apply_start`, 문항에 답을 쓰고 칸을 벗어날 때 `question`, 제출할 때 `submit`을 기록한다. `submit`은 `submit_application` 안에서 기록한다.
- 기록 실패는 화면을 막지 않는다.
- 끝 기준: 로컬 DB 테스트에서 종류별로 한 줄씩 기록된다. 같은 블록을 같은 날 두 번 보내면 한 줄만 남는다. 게시되지 않은 공고는 거절된다.

### S4. 새 공고 알림

- `notice_eligibility` 함수를 만든다. `contract.js`의 `eligibility()`와 같은 결과를 내야 한다.
- 같은 입력 표를 JS와 SQL에 넣고 결과를 비교하는 테스트를 둔다. 기존 6종, `custom`, 빈 값, `cu12Course`를 포함한다.
- 공고가 `published`로 바뀔 때 `fail = 0`인 학생에게 `notifications`를 만드는 트리거를 만든다. 담당자 계정은 뺀다. 프로필의 필수 3칸이 빈 학생은 뺀다.
- 알림 화면에 새 공고 알림을 넣는다. 공고 제목, "지원 조건 m/n 충족", 마감일을 보여 준다. 누르면 `?src=alert`를 붙여 상세로 간다.
- 읽으면 `read_at`을 채운다.
- 알림 화면의 "카카오톡 발송은 연결되지 않았습니다" 문구는 그대로 둔다.
- 끝 기준: 로컬 DB 테스트에서 조건이 맞는 학생만 알림 줄이 생긴다. 미충족 학생, 담당자, 프로필이 빈 학생은 생기지 않는다. 같은 공고를 다시 저장해도 줄이 늘지 않는다.

### S5. 내 정보

- 가입 직후와 로그인 후에 학과, 학년, 재학 상태 중 하나라도 비어 있으면 정보 입력 화면을 띄운다. 이 셋은 필수다. 나머지는 "나중에 입력"으로 넘길 수 있다.
- 기존 프로필 창을 "내 정보" 화면으로 바꾼다. 메뉴에 "내 정보"를 추가한다.
- 내 정보 화면 구성: 기본 정보, 자격 정보, 확인된 자격, 확인 대기 중인 자격.
- 프로필에 학번과 연락처를 추가한다. 가상 정보를 넣으라는 안내를 붙인다.
- 확인된 자격과 대기 중인 자격은 `student_qualifications`에서 읽는다.
- 끝 기준: 단위 테스트로 필수 3칸이 빈 프로필에서 입력 화면이 필요하다고 판정되는지 확인한다.

### S6. 자기 신고

- 신청서의 자격 확인에서 `custom` 자격이 확인되지 않았으면 "충족함" 선택과 설명 칸을 보여 준다.
- 제출할 때 `claims`로 보낸다. `submit_application`이 `student_qualifications`에 `claimed`로 넣는다. 이미 `verified`인 줄은 건드리지 않는다.
- 신청서와 내 정보에서 "확인 대기"와 "확인됨"을 구분해 보여 준다.
- 끝 기준: 로컬 DB 테스트에서 신고가 `claimed`로 들어간다. 학생이 직접 `verified`로 바꾸지 못한다.

### S7. 시연 데이터

- `scripts/seed-demo.mjs`를 만든다. 가상 학생 40명의 계정, 프로필, 행동, 신청서를 넣는다.
- 대상은 스크립트에 넘긴 공고 id 3개다.
- 단계가 내려갈수록 사람이 줄게 한다. 특정 블록과 특정 문항에서 눈에 띄게 줄게 한다. 유입은 네 가지를 섞는다.
- 계정 아이디는 `demo01`부터 `demo40`까지다. 이름은 "가상 학생 01"처럼 가상임이 드러나게 한다.
- 접속 정보는 환경 변수로 받는다. 코드에 키를 쓰지 않는다. 실행은 아침에 사용자가 한다.
- 지우는 스크립트 `scripts/seed-demo-clean.mjs`도 만든다.
- 끝 기준: 로컬 DB에서 스크립트의 데이터 만드는 부분이 끝까지 돈다.

## 다 끝나면

2. 아래 "진행 기록"을 마지막으로 정리한다.
3. 멈춘다. 합치기, 배포, push는 하지 않는다.

### 최종 확인

- S1부터 S7까지 순서대로 커밋했다.
- 마지막 점검에서 일반 클릭으로 연 알림 상세의 주소에 `?src=alert`가 남도록 고쳤다. 공개 공고 목록에서 학교 원문을 바로 열 수 있게 했다.
- 마지막 변경 후 `npm run build` 성공, `npm test` 105개 통과, `npm run test:db` 전체 통과. 학생 전용 DB 검증은 22개다.

### 기본값으로 정한 것

- 마감 시각이 없으면 한국 시간으로 마감일이 끝날 때 접수를 닫는다. 마감 근거가 충돌하거나 마감일이 비어 있으면 접수를 열어 둔다.

- 기수별 조회 집계를 유지하기 위해 기존 5인자 record_event에 더해 옵션 조회용 6인자 호출을 지원한다. 제출 이벤트는 신청서 저장과 같은 트랜잭션에서만 만든다.

- 자기 신고 설명은 선택이며 최대 500자다. 신청 취소나 이후 제출에서 선택 해제해도 이전 자격 이력은 보존한다.

- 시연 계정은 demo01부터 demo40까지다. 공고를 넘긴 순서로 조회 40명, 36명, 32명과 제출 13명, 9명, 5명을 만든다. 두 번째 블록과 두 번째 문항에서 각각 11명과 6명이 줄어든다.

### 통합 요청

- public/privacy.html의 담당자 열람 범위를 갱신해야 한다. 사이트로 제출한 신청서, 제출 시점 프로필, 자기 신고 설명은 해당 공고 담당자가 읽는다. 기존 외부 신청의 준비 답변은 학생만 읽는다.

### 못 한 것과 이유

- 학생 묶음의 로컬 검증은 모두 마쳤다. 브라우저 실측과 실제 Supabase Auth 계정 생성 및 삭제는 밤 작업 범위에서 제외했다.

### 아침에 확인할 것

- 통합 후 담당자 미리보기, 신청자 목록, 자격 확인, 집계 화면에서 학생 화면과 같은 공고로 확인한다.
- 시연 데이터를 넣을 때 학생 마이그레이션 202611260101~202611260105가 적용된 환경과 게시된 사이트 신청 공고 UUID 3개를 사용한다. 공고에 블록과 문항이 2개 이상이면 구간별 이탈을 비교할 수 있다.
- 서버 측 터미널에 SUPABASE_URL, SUPABASE_SERVICE_ROLE_KEY를 설정한다. 시연 계정으로 로그인하려면 첫 생성 전에 CUK_DEMO_PASSWORD를 설정한다. 생략하면 계정별 임의 비밀번호를 생성한다.
- 생성 명령은 `node scripts/seed-demo.mjs <공고1_UUID> <공고2_UUID> <공고3_UUID>`다. 정리 명령은 `node scripts/seed-demo-clean.mjs`다. 정리는 생성 표시가 있는 시연 학생 계정과 연결된 데이터를 지운다.
